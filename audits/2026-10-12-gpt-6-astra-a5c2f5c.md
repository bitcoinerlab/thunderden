# Independent security review: Thunder Den

**Review date:** 2026-10-12

**Reviewer:** OpenCode coding agent using OpenAI GPT-6 Astra
(`openai/gpt-6-astra`), operating as a single tool-assisted AI reviewer.
**Reasoning effort:** `xhigh` (confirmed by the user).

**Provenance metadata recorded:** 2026-10-12 16:40:31 +02:00
(14:40:31 UTC). This is the time this metadata was added, not the original
audit's start or completion time.

**Reviewed repository revision:** `a5c2f5c7f0b39bdba485d9bfd2550d44c2d804e7`

**Intended use assessed:** a self-built USB image, used with Sparrow, Keeper or
the referenced Liana fork, to protect large Bitcoin holdings.

**Method:** independent AI-assisted source review, existing test execution and a
targeted adversarial experiment. This is not a professional audit certification,
a formal proof, or a claim that every dependency has been audited.

## Executive conclusion

**I would not use this revision as the sole signing security boundary for large
sums of bitcoin. Building the image yourself does not change that conclusion.**

The project has real, carefully implemented protections: a storage/network-disabled
kernel design, a separately confined scanner, exact script-based ownership checks,
seed-bound wallet authorization and local approval of an immutable transaction.
The README's core architectural claims are substantially supported by the code.
I did not identify an intentional private-key export/backdoor or demonstrate a
QR-only bypass of transaction approval in the reviewed paths.

However, that is substantially weaker than demonstrating suitability for large
holdings. Important issues are:

1. **An acknowledged compact-PSBT fee attack remains possible.** The software
   permits signing after a warning. A compromised wallet can combine signatures
   from separate low-fee-looking reviews into a transaction with a much higher
   real fee. The repository itself contains a successful attack test.
2. **The ordinary Sparrow/Keeper workflows lack general on-signer receive-address
   verification.** The signer can protect an outgoing transaction while doing
   nothing to stop a compromised coordinator from substituting the address to
   which you initially deposit funds.
3. **Very high-index change is accepted without a mandatory recovery warning.**
   An additional experiment confirmed successful signing with change at indices
   `1,000,000,000` and `2,147,483,647`. The mandatory review hides the address and
   index behind an aggregate “Verified change” total. Normal recovery discovery
   can miss those coins.
4. **Self-building does not authenticate later boots or remove laptop trust.**
   The image is unsigned, Secure Boot is disabled in the documented workflow,
   and an altered image or compromised firmware can capture the seed and use the
   outgoing QR channel to disclose it.
5. **The evidence is still preview-stage.** A fresh full clean-build comparison
   for the latest release and broader physical validation are explicitly pending.
   The local image present during this review also differs from documented
   preview 6; see the artifact warning below.

For test funds, the implementation is a credible experimental signer. For
significant savings, I would first address the high-priority issues and use a
well-tested custody design with independently implemented signers and genuinely
independent keys. If Thunder Den is included, one key in a carefully verified
2-of-3 multisig arrangement limits the consequences of one compromised signer.
Loading all cosigner seeds into the same laptop defeats that independence.

There is no defensible numerical probability of loss from this review. Security
depends strongly on whether the coordinator, build machine, boot media, laptop,
firmware, backup process and human verification are trustworthy.

## 2. Threat model: what “airgapped” does and does not protect

The most important adversary is a compromised online coordinator that controls
wallet setup data, QR images, PSBT metadata and the addresses shown on the online
screen. It must be possible to reject its proposals using trustworthy information
on the offline signer and authenticated information about the intended payment.

Scanner compromise is a separate escalation: the attacker first exploits image
or QR decoding, then needs to escape confinement or exploit the signer's decoded
data handling to reach keys. The separation makes that materially harder.

Compromised signer code, kernel, firmware or hardware is outside that protection.
The laptop sees the entire mnemonic/passphrase and holds usable private keys.
The screen/QR return path is an intentional outbound data channel. Malicious
signer code could encode secrets in extra PSBT data or signatures; absence of
Ethernet and Wi-Fi does not prevent this. No anti-exfiltration/anti-klepto protocol
is implemented to address a malicious signer, and such a protocol would not cure
all hardware or display compromise anyway.

An ordinary infected OS on the laptop's disk does not automatically continue
running after a clean USB boot. Persistence in firmware, an altered USB or a
physical implant is a different threat. An old laptop's history therefore
matters, even though its disks are unavailable to the intended running kernel.

## 4. Findings and suggested fixes

Severity reflects the large-holdings use case and stated prerequisites. A
documented design limitation is identified as such; it is not presented as a
newly discovered implementation exploit.

| ID | Priority | Finding | Evidence level |
| --- | --- | --- | --- |
| F-01 | High | Allowed compact SegWit signing can conceal a much higher real fee | Existing executable attack regression passed; intentional documented tradeoff |
| F-02 | High | Direct wallet workflows lack general trusted receive-address verification | Source and workflow inspection |
| F-03 | Medium | Arbitrarily high change indices bypass mandatory recovery-risk disclosure | Independently reproduced with valid signatures |
| F-04 | Medium | Documented Liana installation follows moving software versions | README and limited external source inspection |
| L-01 | High impact, conditional | Unsigned boot and laptop/firmware trust can defeat all signer protections | Documented architectural limitation; no physical exploit attempted |

### F-01 — Compact multi-input SegWit fee attack remains possible

**Location:** `src/transaction.cpp:383-388,420-461`,
`src/application.cpp:36-43`, `src/review.cpp:207-215`,
`tests/transactions.cpp:550-568`, `docs/FEES.md:40-77`.

For SegWit v0, an ALL signature commits to its own input amount but not the amounts
of the other inputs. Where those other amounts lack full previous transactions,
Thunder Den flags the fee as unverified. It nevertheless releases signatures
after the warning and ordinary `SIGN` confirmation.

A concrete example already exercised by the repository is:

| | Actual transaction | Request 1 | Request 2 |
| --- | ---: | ---: | ---: |
| Input A | 100,000 sats | 100,000 sats | 100 sats |
| Input B | 100,000 sats | 100 sats | 100,000 sats |
| Outputs | 100,000 sats | 100,000 sats | 100,000 sats |
| Fee | **100,000 sats** | **100 sats, unverified** | **100 sats, unverified** |

The transaction's outpoints and outputs can be identical across requests. The
coordinator takes the valid signature for A from the first reply and the valid
signature for B from the second. Core verifies the resulting high-fee transaction
against the real previous outputs. The bad signatures for the lied-about inputs
are discarded. Loss can scale far beyond these example amounts.

The confirmation is not bypassed: the user must accept the warning and sign.
The issue is that approval cannot make the displayed fee trustworthy. A retry
pretext is one route, but collecting signatures through different participants,
accounts or sessions also matters. Multisig alone does not prevent the attack if
the required participants all permit these unsafe signing requests. The excess
becomes a miner fee; direct attacker recovery of that value is not necessary for
the victim to lose it.

The UI warning says “This is usually fine” and “Otherwise, this warning is expected
and you can continue.” This is weaker than `docs/FEES.md`, which correctly states
that accepting the warning does not prevent the attack. Users handling large
holdings should not be trained to treat it as routine.

**Suggested fix:** make `fee_unverified` fail closed for the normal custody flow.
Require full previous transactions wherever the signatures being released do not
commit to all otherwise unauthenticated amounts. Preserve compact support where
it is cryptographically sufficient: for example, a single-input SegWit-v0 spend,
or the applicable Taproot DEFAULT signing case. Test coordinator support for the
larger PSBTs. Rewrite the warning to state possible substantial loss plainly if
an explicitly advanced compatibility override remains.

**Current-user mitigation:** cancel every “fee not fully verified” signing request
for significant funds. Rechecking the fee on the same possibly compromised
coordinator is not an independent fix. A fee cap calculated from the same
unauthenticated amounts would not fix it either. Do not switch a complex wallet
to Taproot merely to silence a warning without reviewing the new policy.

### F-02 — Receiving is insufficiently protected in the direct workflows

**Location:** `src/main.cpp:128-181`, `src/transport.cpp:61-65`,
`src/review.cpp:55-68`, `src/qr_commands.cpp:83-94`,
`docs/SPARROW.md:67-88,119-140`, `docs/KEEPER.md:15-28,57-67`.

The main menu offers scanning, xpub export and session end. It has no local address
browser or address-verification action. The scanner accepts UR PSBTs, wallet
setups and Thunder Den commands; a conventional address/BIP21 QR is not a general
receive-address verification input.

Multisig registration displays receiving index 0, which is a useful check when
performed **before funding**. It does not let the ordinary direct flow verify an
arbitrary later receive address. Standard single-signature export displays the
xpub and path, not a locally derived receiving address.

The custom command protocol does support address verification. The inspected
async-hwi adapter uses it for the Liana integration. That feature should not be
mistaken for availability through Sparrow's SeedSigner or Keeper's Jade profile;
the documented direct flows do not implement that general check.

**Attack:** an infected coordinator imports the correct Thunder Den xpub but
shows an attacker-controlled address in its Receive screen. The user deposits
large funds there. Thunder Den is never asked to sign those funds and cannot
prevent the theft. Correctly verifying an exported xpub once does not authenticate
every future address displayed by the coordinator. A successful earlier small
test deposit also does not authenticate a later large-deposit address.

**Suggested fix:** add a fully local receive-address display/verification flow
for standard accounts and the approved multisig policy, with explicit account,
network and index. Alternatively, expose a compatible request flow in each
coordinator that causes the signer to derive and display the requested address.
The signer must derive the address itself; merely redisplaying an imported address
is not verification. Document verification of the actual deposit address before
funding, and add integration coverage for it.

**Current-user mitigation:** independently derive and compare the complete actual
deposit address on a trusted offline device or another verified signer with the
correct full wallet policy. For multisig, index 0 can be checked during registration
after authenticating the cosigner keys. Comparing two screens whose address text
comes solely from the same untrusted coordinator is insufficient.

### F-03 — High-index change can make ordinary recovery miss funds

**Location:** `src/policy.cpp:280-305`, `src/transaction.cpp:77-98,408-415`,
`src/review.cpp:104-112,140-141,196-203`.

Ownership matching accepts every unhardened address index through `2^31 - 1`.
Once an output matches the approved policy's change branch, the mandatory review
shows only aggregate change amount/count. The full address and index are available
only in optional Details. There is no unusual-index warning.

An adversarial synthetic probe confirmed this for:

| Wallet | Tested change indices | Result |
| --- | --- | --- |
| Standard BIP84 | 1,000,000,000; 2,147,483,647 | Accepted; mandatory summary omits address/index; signature verified |
| Standard BIP86 | 1,000,000,000; 2,147,483,647 | Same |
| 2-of-2 native SegWit multisig | 1,000,000,000; 2,147,483,647 | Same; both cosigner passes completed and verified |

These fixtures included full previous transactions and a verified 1,000-sat fee;
the issue is independent of F-01.

**Impact:** a malicious coordinator can direct legitimate change to an address
far beyond ordinary gap-limit discovery. The keys still control the coins; this
is not an attacker-address substitution or proven permanent destruction. It can
nevertheless cause apparent loss, difficult recovery or an extortion opportunity
if the coordinator withholds the index and wallet records are lost. The blockchain
does not directly encode the BIP32 derivation index. Known transaction history
and retained paths substantially improve recovery.

**Suggested fix:** distinguish “belongs to this policy” from “ordinary recoverable
change.” Show change indices in mandatory review and require a prominent warning
or explicit exceptional flow for unusual output indices. A stateless signer cannot
know the coordinator's genuine last-used index, so define a conservative normal
range rather than trusting a host-supplied last-used value. Continue to support
spending existing high-index inputs; blocking those would worsen recovery.

**Current-user mitigation:** inspect every change output's index in Details,
reject surprising large jumps, and preserve public wallet metadata/transaction
history. Seeds and descriptors alone do not specify the last used indices.

### F-04 — Liana/bridge setup is not pinned by the README workflow

**Location:** `README.md:94-107`, `docs/STATUS.md:64-92` and the external source
files listed in Scope.

The documented installation builds the Liana fork from its moving `master` and
runs:

```sh
npx @bitcoinerlab/thunderden-qr-bridge
```

That command does not identify the reviewed/tested package version. Depending on
the installation/cache state and later publishing, users can execute different
code than the documented `0.1.2` release. The bridge executes on the online
coordinator, so a compromised release would give it that host's user privileges.
An honest, correctly used signer should still resist unauthorized signing, but
coordinator compromise enables the proposal/deposit/fee attacks discussed here.

The limited source check found positive controls: the bridge binds to loopback,
checks Host/Origin, bounds requests and correlates replies; the async-hwi adapter
checks request IDs/network, registration wallet IDs and preservation of the
unsigned transaction. I did not demonstrate a bridge exploit. Those controls do
not authenticate a future package version fetched by an unversioned command.

**Suggested fix:** document exact tested commits for Liana and its adapter, an
exact bridge version, and a verifiable release/build manifest. Pin transitive
dependencies with the lockfile and verify provenance/integrity of the installed
artifact. An explicit `@0.1.2` would identify the documented version, but version
pinning alone is not an endorsement or a substitute for source/package review.
Record and retest upgrades deliberately.

### L-01 — Unsigned boot and general-purpose laptop trust remain critical

**Location:** `README.md:31-35,113-131`, `docs/BUILD.md:64-68`,
`platform/grub.cfg`, `build/image.py:72-90`.

The documented boot path loads an unsigned GRUB/kernel image with Secure Boot
disabled. There is no shown chain that authenticates this image to an independently
trusted key on each boot. Runtime non-writability cannot stop another computer,
an installed OS or a physical attacker from changing the USB before a future boot.

A replacement image can present the expected screens, collect recovery words and
later leak them through the QR reply. Firmware or a keyboard/physical implant can
similarly defeat the software. RAM-only operation does not address these attacks,
nor cold-boot/DMA-style extraction of a live session. This limitation is partly
disclosed in the README; no exploit of the actual laptop was attempted.

**Suggested improvements:** support and test an owner-controlled authenticated
boot chain, including the kernel, initramfs and relevant boot configuration; verify
boot-media contents from a trusted system against an independently retained hash;
use physically controlled media and a dedicated, maintained laptop. Owner-controlled
Secure Boot would narrow one attack surface, not certify firmware or eliminate
physical attacks. Higher-assurance holdings benefit from signers on independent
hardware with separate seeds and backups.

## 5. Wallet-specific assessment

### Sparrow / SeedSigner profile

- Account exports and single-signature/sorted-multisig signing use the common
  Thunder Den validation/signing engine. The profile name does not import
  SeedSigner's implementation or security assurances into Thunder Den.
- The repository reports real-device tests and a broader headless compatibility
  matrix, but exact physical-test device/version details are incomplete
  (`docs/STATUS.md:94-105,137-148`). This review reran the native tests, not Sparrow.
- Compact multi-input SegWit requests can encounter F-01. General deposit-address
  verification is the gap in F-02. High-index change is not profile-specific.
- PSBT-first multisig setup should not be your first verification of a wallet
  that already holds large funds. Authenticate its complete setup before funding.

### Keeper / Jade QR profile

- The native P2WSH setup importer checks the threshold, account origins, local
  xpub and resulting descriptor. Labels are bounded/ignored as identity; the
  actual keys and scripts matter (`src/wallet_qr.cpp:139-183`).
- Jade here is a compatible QR profile. Thunder Den does not acquire Jade's
  device protections by being selected under that name.
- The recorded physical test was iOS/testnet4 on an earlier inline-setup image;
  exact app/OS versions and broadcast outcome were not separately recorded
  (`docs/STATUS.md:231-243`). It is not evidence of a fully validated large-value
  mainnet deployment.
- F-01/F-02/F-03 apply. Keeper's “registered” state does not persist the policy
  inside Thunder Den after reboot (`docs/KEEPER.md:64-67`).

### Liana fork / async-hwi / browser bridge

- The custom protocol supports persistent seed-bound registration proofs and
  requested address display, giving this integration a better route to trusted
  deposit-address verification than the direct profiles.
- The adapter's reply and PSBT consistency checks are useful. Request IDs and
  fingerprints are correlation/identity labels, not cryptographic proof that the
  online host is honest. The human still compares the full signer-displayed address.
- This is fork-only support, with Liana Connect disabled and a complete physical
  signing flow still listed as outstanding (`docs/STATUS.md:75-92`).
- P2WSH remains subject to the compact-fee condition if insufficient UTXO evidence
  is supplied. Taproot DEFAULT has stronger amount commitments but does not cure
  incorrect wallet policies, compromised boots or failed backups.
- Liana recovery timelocks need a real recovery exercise. Thunder Den explicitly
  does not establish chain maturity. Arbitrary Miniscript registration also shows
  raw rules rather than a full plain-language spending analysis: review every
  branch, recovery key and delay. In Taproot, an internal key controlled by someone
  can provide a key-path spend independent of the apparent script-tree conditions;
  an intended unspendable internal key must be independently validated. This is a
  policy-review requirement, not a demonstrated defect in the referenced fork.

## 6. Important operational boundaries

### Registration is approval of bytes, not proof of your intended wallet

The seed-bound HMAC properly detects changes to an already registered definition
when that proof is supplied (`src/policy.cpp:233-278`). It does not establish that
external cosigners are genuine. The signer can authenticate its own full xpub, not
ownership of every other key.

The direct multisig flows approve a new session-local setup after reboot. A valid
new `REGISTER` operation is not evidence that it is the same wallet used last time.
The code appropriately asks the user to compare cosigners against their devices
or trusted backup (`src/application.cpp:23-29`). Follow that requirement, including
the threshold and full key/origin information; a four-byte fingerprint alone is
not a cryptographic ownership proof.

An important protection should not be understated: a substituted policy does
**not** automatically spend already-funded inputs belonging to the original
policy. Exact script matching blocks that straightforward change-substitution
attack. The remaining danger is approving/funding the wrong initial or replacement
wallet, or misinterpreting an intentionally more permissive policy.

### Backups must include the public wallet configuration

For multisig/Miniscript, retain the complete descriptors/policies, all cosigner
xpubs and origins, thresholds, branches, network, account information, recovery
conditions and relevant derivation history, alongside independently protected
seed/passphrase backups. The registration HMAC is not a wallet backup. Test
reconstruction on independently trusted software/devices before substantial
funding. Plan for loss of the laptop, USB, coordinator and one cosigner.

### Seed provenance matters

Thunder Den imports existing BIP39 words; it does not generate a new mnemonic
(`docs/DESIGN.md:31-46`). A seed previously exposed to an online wallet, camera,
cloud backup or compromised device does not become safe when imported here.
For a new custody setup, generate independent seeds with a trusted offline method
and test backup restoration. English words and printable-ASCII passphrases are
explicit compatibility limits; preserve exact passphrase case and spaces.

Ending a session destroys managed key state and exits the process. It is not
verified complete physical-RAM sanitization. Use a full power-off and maintain
physical control; do not leave a loaded signing session unattended.

## 7. What I would require before using this for large holdings

1. **Close the receive-address verification gap and reject unverifiable fees.**
   These are directly relevant to an infected online wallet, not exotic hardware
   threats. Every intended deposit and payment address needs a trustworthy check.
2. **Address exceptional change paths.** Show/confirm change indices and test
   recovery after loss of coordinator history, including F-03's edge cases.
3. **Build an identified source revision in fresh volumes on a trusted builder.**
   Verify upstream pin provenance; run the native suites and packed-image checks.
   Independently reproduce the final image where feasible, retain its manifest
   and hash, and verify the flashed bytes. Do not treat the existing unmatched
   local image as the audited artifact.
4. **Validate that exact image and wallet versions on the intended hardware.**
   Exercise setup, address verification, single/multi-input signing, change,
   refusal, QR retries, reboot/re-registration and complete recovery using test
   funds. For Liana, include the delayed recovery spending path. A successful
   round trip is compatibility evidence, not a substitute for hostile-host tests.
5. **Get independent specialist review of the remaining high-value boundaries.**
   Priorities are PSBT/sighash assurance, policy semantics, UI authorization,
   signer-side parser robustness and the production boot image. Add sustained
   fuzzing/sanitizer coverage of PSBT/policy/CBOR inputs and the scanner IPC parser.
6. **Limit single-device consequences.** Use independent cosigners and independently
   authenticated wallet backups; never enter multiple threshold keys into the same
   Thunder Den laptop. A redundant threshold such as 2-of-3 can tolerate one lost
   signer while requiring more than one compromised key to steal funds, provided
   the wallet policy and deposit addresses were genuinely verified.

## Appendix: reproducible evidence for F-03

The additional probe used `tests/multisig_fixture.h` to make a funded synthetic
PSBT, then performed the following for BIP84, BIP86 and 2-of-2 P2WSH:

1. Construct the usual policy and a `fixture::Spend({&policy})` request, retaining
   the full previous transaction.
2. For each index `1,000,000,000` and `2,147,483,647`, replace output 0's script with
   `policy.Script(1, index)` and reset its PSBT output metadata.
3. Call `UpdatePSBTOutput(policy.PublicProvider({1, index}), psbt, 0)` so the hints

All six combinations succeeded. No production auto-approval mode was added; this
tested the library's existing approval interface. The probe did not test a real
wallet's recovery scan and does not claim the funds are mathematically unspendable.
Its confirmed result is acceptance, summary omission and valid signatures.

**Bottom line:** Thunder Den's implementation deserves credit for its explicit
trust boundaries and meaningful checks. At this revision, those checks still
leave practical host-wallet and recovery risks, and the release evidence does not
justify relying on one self-built Thunder Den laptop for large Bitcoin savings.
